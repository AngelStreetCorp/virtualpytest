# `ai-dataset` — optional feature

The **review side** of the AI training dataset (TASK-27 step 4): an admin page where a
human checks captured AI training samples against one plain question, labels them, and
freezes an eval set; the `/server/training-samples/*` routes behind it; a read-only
script that mines review candidates; the step 5 scoring (family prompts, comparators,
`scripts/score_eval.py`); and the step 6 read-only export of the combined training
dataset for the top-level `training/` folder (`scripts/export_dataset.py`); and the step 4h
seed of `screen-id` samples from the navigation node screenshots plus the coverage report of
the canonical apps (`scripts/seed_from_trees.py`, `scripts/coverage_report.py`,
`GET /server/training-samples/coverage`, the *Coverage* panel); and the step 4i AI triage,
where an AI worker labels in place of the human and the human only sees disagreements and a
spot-check (`scripts/triage_batch.py`, the *Needs you* view, the `eval-v0-ai` freeze, and the
feature's own migration `db/001_triage.sql`); and the step 4k screen groups, where a
`screen-id` answer is the screen (Home with any tab focused is `home`) and the focused item is
its own question (`lib/screen_group_scope.py`, `scripts/regroup_screen_labels.py`,
`GET /server/training-samples/screen-groups`); and the step 4l focus-text pass, where the AI
worker reads the visible text of the focused tab or tile of a grouped `screen-id` row
(`scripts/focus_text_pass.py`).

**Capture is core, not this feature.** The helper that records samples, its DB module,
the table, the capture hooks and the training bucket client stay in core and are inert
unless `TRAINING_DATA_ENABLED` is set. With this feature disabled, samples are still
captured (if capture is on) and simply cannot be reviewed from the UI.

Packaged per `docs/technical/FEATURES.md`. Disable with `DISABLED_FEATURES=ai-dataset`
(and `VITE_DISABLED_FEATURES=ai-dataset` for the frontend build; the deploy scripts set both).
Design and history: `docs/tasks/TASK-27-ai-training-dataset.md` (§7, §8, Step 4, Step 4d, Step 4e, Step 4f, Step 4g, Step 4h, Step 4i, Step 4j, Step 4k, Step 4l, Step 5, Step 6, Step 7).

## Freeze options (step 4i)

| Version | Takes | Minimum |
|---|---|---|
| `eval-vN` (e.g. `eval-v1`) | eval rows with `label_source='human'` | 200 |
| `eval-vN-ai` (e.g. `eval-v0-ai`) | human rows **plus** AI-verified rows (`triage.status='agreed'`: the AI teacher agreed with the run label) | `min_rows`, default 50 |

`score_eval.py --eval-version eval-v0-ai` reports that set as `labels: human+AI (mixed)`. A row
has one `eval_version`: human rows frozen into `eval-v0-ai` can no longer enter `eval-v1`.

## Admin only

The routes need `ai.training:view` (list, eval-counts, offtree-labels, coverage) and `ai.training:review` (label,
freeze). Both are in `ADMIN_ONLY_PERMISSIONS`: no role other than admin can hold them, so
only an admin (or a user given an explicit individual grant) passes.

The page and the menu entry use **the same permission, through the existing path-keyed
layer**, with no feature-specific guard:

- Feature routes render inside the core `<Route element={<ProtectedRoute />}>` group of
  `App.tsx`. `ProtectedRoute` falls back to `requiredPermissionForPath(pathname)`, which
  reads `PAGE_PERMISSIONS['/training-review'] = 'ai.training:view'` in
  `frontend/src/types/auth.ts`. A non-admin who opens the URL gets *Access Denied*.
- Nav items (core or feature) go through `Navigation_Dropdown` → `isPathHidden(path)`,
  which reads the same table. A non-admin never sees *AI Dataset* in the AI dropdown.

So `FeatureDefinition` needed no `requiredRole` extension. This is the same mechanism the
`quicktest` (`/builder/quick-test`) and `cicd` (`/test-execution/cicd`) pages use.
