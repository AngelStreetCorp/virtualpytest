# 2048 Showcase (`game_2048`)

## Purpose

Plays 2048 on **any device**, a browser on a host or Chrome on an Android phone, with **one script**,
and reports the final score, the moves and the AI usage as KPIs (TASK-33). It shows that VirtualPyTest
drives any perception–actuation target through its normal stack:
- a user interface (navigation tree) per platform;
- the navigation, action and verification executors;
- a board read from captured frames;
- a move chosen by an LLM through the AI gateway, or by a fixed rule.

## How it is built

| Piece | Where | Role |
|---|---|---|
| Script | `test_scripts/game/game_2048.py` (script id `game/game_2048`) | Resolves the user interface, loads its tree, runs the game, writes KPIs. No device code |
| Game library | `shared/src/lib/game2048/` | `board.py` (rules), `player.py` (heuristic + LLM), `reader.py` (pixel board reader), `runner.py` (loop, report, metadata) |
| User interfaces | `game2048-web`, `game2048-android-mobile` | Same tree, platform-specific actions and checks. Built by `scripts/game2048_ui.py` |
| Controller | `android_mobile` `open_url` command | Opens a URL (VIEW intent) in a given browser package |

The tree is the same on both platforms:

```
Entry → game ─┬─ move_left / move_right / move_up / move_down   (action nodes)
              ├─ new_game                                        (action node)
              └─ game_over                                       (checked, no action)
```

| | `game2048-web` (models: web, runs on host_vnc) | `game2048-android-mobile` (models: android_mobile) |
|---|---|---|
| Entry → game | `open_browser`, `navigate_to_url`, JS: accept necessary cookies, JS: zoom 0.55 (whole board on the 1280×720 VNC screen) | `open_url` in `com.android.chrome` |
| move_* | `press_key` LEFT / RIGHT / UP / DOWN | `swipe` across the board centre (540, 1424) on a 1080×2340 screen |
| new_game | JS: click New Game, accepting its `confirm()` | tap New Game (885, 884), `click_element` "OK" on the Chrome dialog (there is no dialog after game over, so this step fails there and the runner reads the screen anyway, BUG-0218) |
| game check | web `waitForElementToAppear` `.restart-button` | text (OCR) `waitForTextToAppear` "2048" in the title-row area (480, 180, 320×120) |
| game_over check | web `waitForElementToAppear` `.game-over` | text (OCR) `waitForTextToAppear` "Game over" in the board area (490, 290, 300×300); full-frame OCR misses it (BUG-0217) |

To change a tree, edit `scripts/game2048_ui.py`, build the bundles
(`python scripts/game2048_ui.py --out <dir>`), and import them with `POST /server/userinterface/import`,
replacing the old user interface.

## Usage

```bash
python test_scripts/game/game_2048.py --max_moves 10                  # quick check, auto user interface
python test_scripts/game/game_2048.py --player heuristic               # full game, no model
python test_scripts/game/game_2048.py --userinterface game2048-web     # force a user interface
```

## Parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `--userinterface` | string | `auto` | `auto` picks the `game2048-*` user interface whose models match the device. It also overrides a device's own default user interface |
| `--player` | `llm` \| `heuristic` | `llm` | Who picks each move |
| `--max_moves` | int | `3000` | Move budget. The run stops there and passes (`stop_reason=move_limit`); the floors only apply to full games |
| `--max_duration` | int | `3600` | Hard stop in seconds. Reaching it fails the run (`stop_reason=time_cap`) |
| `--min_score` | int | `500` | Pass floor for a full game's score |
| `--min_tile` | int | `64` | Pass floor for a full game's highest tile |

## Reading the board from pixels

The reader never uses OCR. It works the same on VNC (web host) and HDMI (phone) captures.

1. **Locate the board** by its background colour: the largest near-square blob.
2. **Tile colour** is the median colour of each tile's inner area; the median ignores the digit strokes.
3. **Fresh board:** exactly two 2/4 tiles, seen identically on two different frames.
4. **After each move (tracking):** the script knows the board and the move, so it predicts the result.
   A frame is accepted when:
   - every predicted-empty cell is empty,
   - every predicted tile shows its predicted value (tiles below 128 must match exactly),
   - exactly one new 2 or 4 has appeared,
   - and two **different** frames agree.

   These conditions reject frames caught mid-slide or mid-spawn. A new tile scaling in looks like a 4.
   A pre-move frame of a merging move looks like "predicted + one new tile".
5. **Palette:** every confirmed tile's colour is learned, which calibrates the reader to each capture
   pipeline (HDMI brightens colours by about +18/+15/+8 RGB).
6. **Resync:** if no frame matches within 5 s, a blind read is used (counted in `board_resyncs`). It
   never invents a tile above twice the current biggest. If the board is unchanged, the move counts as
   not applied; 3 of those in a row stop the run.

**Score** is the sum of each move's merges, computed from the board, so no OCR is needed.

## Players

- **`llm`:** one AI-gateway call per move, usage `text.game_2048`. The prompt has the board, every
  legal move with its resulting board, the points and the empty cells it leaves, and a corner-strategy
  tip. The model answers `{reasoning, move}`.
  - The route decides the model. Today it is `qwen3-4b-pc-local` (`qwen/qwen3-4b` in LM Studio, no cloud
    fallback, profile extra `{"reasoning_effort": "none"}`).
  - A failed call or an illegal answer falls back to the heuristic for that move (`heuristic_fallback`).
    After 3 failures in a row, the heuristic plays the rest of the game.
- **`heuristic`:** a fixed priority `LEFT > DOWN > RIGHT > UP`. No model, no tokens.

## Report

The report has one step per move: the navigation step of that move, enriched with the decision.
- **Message:**
  - LLM: `Move 7: DOWN by qwen/qwen3-4b (+8, score 40) - keeps the 16 in the corner`.
  - Heuristic: `Move 3: LEFT / DOWN blocked -> RIGHT (+0, score 4)`.
- **Actions:**
  - `ai.gateway.complete` (model, profile, endpoint, tokens in/out, latency). Only on LLM moves.
  - The tree's own action: `press_key` or `swipe`.
- **Verification "Decision and board":** reasoning, legal moves, raw answer, board before/after, read
  status, points, move-to-settled-board time.
- **Screenshot:** the settled board.

Plus the `Entry → game` step, a "Fresh board" step, the `game → game_over` step (with its check), and
the KPI step. The summary shows the user interface, the player, the models and endpoints, decisions by
player, tokens in/out, and board resyncs.

## Outputs and Metadata

`script_results.metadata` holds:
- `final_score`, `max_tile`, `move_count`, `moves_by_direction`, `stop_reason`, `reached_2048`
- `path` (`web` / `android-mobile`), `userinterface`, `device_model`, `player`, `strategy`
- `llm_usage`, `llm_calls`, `tokens_in`, `tokens_out`, `avg_llm_ms`, `llm_models`, `llm_endpoints`, `decisions_by`
- `play_duration_s`, `avg_move_ms` (move to settled board), `board_resyncs`, `final_board`

Grafana: the **2048 Game** dashboard (uid `game-2048`,
`infra/monitoring/grafana/dashboards/game-2048.json`) has filters for platform (`path`) and player.
- Stat tiles: runs, full games, pass rate, best score, best tile and LLM tokens.
- Time series: the final score of each full game, and seconds per move.
- A table of runs, with a link to each report.

**AI usage.** With `--player llm` the summary ends with an AI block (model, total tokens in/out, and per move:
tokens in/out and ms); the same lines are in the run log and `ai_usage` in the metadata. `--player heuristic` says `AI: none`.

A **full game** is a run whose `stop_reason` is `game_over` or `game_over_not_confirmed`. Quick
checks (`move_limit`) and early failures are left out of the score panels. The seconds-per-move panel
only counts runs that have a `userinterface`, which leaves out the phase-1 runs that read the DOM.
As in every dashboard, `_apply_device_scope.py` wraps each `script_results` read in the viewer's device scope.
