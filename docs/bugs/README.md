# 🐛 Bug Tracker

> Release notes: [../release_note/README.md](../release_note/README.md)

Lightweight, in-repo bug log. **One markdown file per bug** (full symptom / root cause / fix /
verification); this page is the index. Every user-facing fix gets a file — that detail is the point.

## How to log a bug

1. Copy [`_TEMPLATE.md`](_TEMPLATE.md) to `BUG-<NNNN>-<YYYY-MM-DD>-<slug>.md`, where `<NNNN>` is the
   next sequential ID (zero-padded) and `<YYYY-MM-DD>` is the reported date.
   Example: `BUG-0002-2026-07-16-player-24h-reload.md`.
2. Fill in the meta table + **Symptom / Root cause / Fix / Verification** — the whole point of a
   file per bug is that the detail lives somewhere durable, so don't skimp.
3. Add a row at the **top** of the Index table below (newest first), linking to the file.
4. When the fix ships, set **Status**, **Fixed in** (build number) and **Commit** here **and** in
   the bug file, and add a matching one-line entry under the correct release in the
   [release notes](../release_note/README.md) (bugs → **🐛 Bug fixes**, linking back to this file).
5. Optional: reference the ID in the commit subject, e.g. `fix(db): index kpi lookup (BUG-0001)`.

> **This tracker is published on the public docs site** (`/docs/bugs`). Write every report as
> if a stranger will read it — no customer names, no customer site hostnames, no lab addresses,
> no credential values. Replacement convention (and why this rule exists):
> `docs/agent/release/ANONYMIZATION.md` (internal). The push-time leak
> gate catches the identifier half; the rest is on the author.

**Status vocabulary:** `Open` · `In progress` · `Fixed (pending deploy)` · `Closed`

> IDs are never reused. `BUG-0007` exists only on this branch (`feat/demo`); on `main` it is
> intentionally absent — the colliding parallel entry there was renumbered to `BUG-0008`.
