## Symptom

Logged into `https://virtualpytest.angelstreet.io`, the selected server is
`https://<pi-server-host>`, and "DOM report" is opened from
`/configuration/interface`. The new tab lands on
`https://<pi-server-host>/server/userinterface/domReport?userinterface=…&team_id=…` and the
server returns:

```json
{"error":"Authentication required","message":"Authorization header is required"}
```

The same call works for any other server the user is logged in to directly (i.e. when the
frontend and the selected server share an origin).

## Root cause

The DOM report endpoint
(`backend_server/src/routes/server_navigation_trees_routes.py:1781-1792`) streams the HTML
directly from the Flask handler. Because it lives under `/server/*`, the global auth guard
(`backend_server/src/lib/auth_middleware.py`) requires a valid credential on every request.

The SPA authenticates by attaching the Supabase JWT to every `/server/*` request
(`frontend/src/utils/installFetchAuth.ts`) and mirrors it into a `vpt_jwt` cookie for
plain browser navigations (`installFetchAuth.ts:46-86`, BUG-0057 fix `0224543ad`).

A `window.open(...)` navigation is a plain browser GET — it cannot carry the `Authorization`
header, so only the cookie matters. The cookie is written host-only with
`document.cookie = "${name}=${value}; Path=/server/; SameSite=Strict; Secure"`. Without a
`Domain` attribute, the browser binds it to the SPA's own host (`virtualpytest.angelstreet.io`)
and does not send it on the cross-origin navigation to `<pi-server-host>`.

`<pi-server-host>` therefore receives a credential-less request and returns 401 from
`auth_middleware._require_user_auth_probe()` (`auth_middleware.py:425-441`).

This is the exact limitation called out in BUG-0057's "Follow-ups" section:
*"cookies are per origin, so a report served by a different server origin than the frontend
(e.g. the rpitest server opened from the main UI) still needs its own session there."*

## Fix

Mirror the pattern the test-reports already use. The DOM report HTML was already being
persisted to R2 by `backend_server/src/services/dom_report.py:265-301`; the new code just
hands the browser a presigned URL for that artifact instead of streaming it through Flask.

**Backend** (`backend_server/src/routes/server_navigation_trees_routes.py`):

- New `GET /server/userinterface/domReport/url` route. Requires user auth. Validates
  `userinterface` + `team_id` (400), checks the UI exists (404), calls `build_dom_report`
  to ensure the artifact is in R2 (idempotent — no-op on cache hit), generates the
  presigned URL via `cf.get_url_for_report_asset('navigation/<safe>/dom_report.html')`
  (signed against `MINIO_PRESIGN_ENDPOINT`, the public proxy that fronts R2), and
  returns `{"success": true, "url": <signed>}`.
- The existing `GET /server/userinterface/domReport` HTML route is unchanged — curl,
  internal callers, and `tests/backend_server/test_navigation_trees.py::test_dom_report_unknown_interface_returns_not_found_html`
  keep working.

**Frontend** (`frontend/src/pages/UserInterface.tsx`):

- The "DOM report" menu item now calls a new `openDomReport(uiName)` helper that does a
  single `api.get('/server/userinterface/domReport/url?...')` and `window.open`s the
  returned URL. The new tab hits the public proxy on the **same origin as the SPA**
  (not on the selected server), so no Authorization header is needed and the cookie is
  irrelevant.

**Tests** (`tests/backend_server/test_navigation_trees.py`):

- `test_dom_report_url_requires_params` — no `userinterface` / `team_id` → 400.
- `test_dom_report_url_unknown_interface_returns_404` — non-existent UI → 404 with
  `success: false`, "not found" in `message`.

**API spec** — `docs/api/specs/server-additional-routes.yaml` regenerated by
`scripts/generate_api_route_specs.py`. New entry under
`/server/userinterface/domReport/url`.

## Why this beats widening the cookie

A `Domain=.angelstreet.io` cookie would fix this single case but is a privacy/footprint
change that affects every `/server/*` navigation, not just the DOM report, and is silent
on the failure mode (the cookie is still host-only on `localhost` deployments and on any
deployment whose servers live on different registrable domains). A signed URL is the same
primitive the rest of the app already uses for "open this report in a new tab" — see
`shared/src/lib/utils/cloudflare_utils.py::get_url_for_report_asset` and
`frontend/src/utils/infrastructure/cloudflareUtils.ts::openR2Url`.
