# BUG-0565

## Symptom
BUG-0562 wired the verify / localize_button / localize_check paths into `match_runs`, but the monitor path was deferred: a direct insert in `MonitorLocalize.localize_frame` would write at ~1 Hz per device, which is 432k rows/day fleet-wide. Most of those rows are noise — same verdict, same screen, every second — and the freeze detector would block on every Supabase round-trip.

A second problem: the matcher profiles (tv_app, pc, drone, counting_cars, ...) run on different devices with different cadences and different matcher thresholds, but the rows they wrote had no profile tag. The dashboard could not separate a `pc` host's quiet match from a `tv_app` host's busy STB, and the auto-classify scheduler's per-host throttling was invisible.

## Fix
A Redis queue + systemd worker between the monitor and Supabase, modeled on the existing `vpt-discard-incidents` pattern. Three channels, one worker, per-profile throttling.

**Storage (migration 20261017a)**
- `public.match_runs.profile text` — the matcher profile (tv_app, pc, drone, ...). NULL for non-monitor sources.
- Partial index on `(team_id, profile, started_at DESC)` for the dashboard's "monitor activity by profile" view.

**Queue (`shared/src/lib/queue/match_runs_queue.py`)**
- `match_runs:queue` — steady-state settled-screen runs (worker throttles to ~1 row / 10s per device)
- `match_runs:queue:change` — verdict CHANGED (every change lands; this is the input to `v_node_transitions`)
- `match_runs:queue:alert` — unknown / low_confidence / no_signal hits (every hit bumps the `screen_fingerprints` counter)
- `push(payload, severity)` and `pop_batch(channel, max_items, timeout_s)` are the two halves; both work on the existing `redis_queue.RedisQueueProcessor` (Upstash REST + local Redis).

**Monitor writer (`backend_host/scripts/monitor_localize.py:MonitorLocalize._enqueue_match_run`)**
- Called at the end of `localize_frame`, after the motion gate / jev-second-opinion.
- Resolves the profile via `shared.src.lib.utils.monitor_profile.resolve_monitor_profile(device_index)` — same helper the host already uses to pick the profile at startup, so the queue tag is always consistent with the running profile.
- Routes to the right channel by checking: (1) is the new `kind` or `node` different from the last emit for this device? → `change`. (2) is the new `kind` unknown / low_confidence / no_signal / live / overlay? → `alert`. (3) otherwise → `normal`.
- Computes a 64-bit dhash of the live frame so the worker can dedupe the `screen_fingerprints` counter across runs of the same unknown screen.
- **Never raises** — a missing Redis just logs at debug and the matcher result is still returned to the caller.

**Worker (`backend_server/scripts/match_runs_worker.py`)**
- One process, three channels in priority order: change → alert → normal.
- `match_runs_worker.service` (`User=vpt_user`, `Type=simple`, `Restart=on-failure`, `RestartSec=10`, `TimeoutStopSec=15`).
- Per `(host, device, profile)` throttle in-memory: 10s default on the steady-state channel. Verdicts changing always emit; alert kinds (unknown / low_confidence / no_signal) bypass the throttle.
- Idle log every 60s with queue lengths, so `journalctl -u vpt-match-runs-writer` shows whether the worker is keeping up.
- `--dry-run` mode for smoke-testing the worker without writing to the live DB.
- Idle loop sleeps 100ms when a cycle is faster, so a quiet monitor doesn't hot-spin the CPU.

**Why three channels and not one**
- A burst of verdict changes (operator pressing Localize 20 times) must not delay the steady-state settled-screen log.
- Alert hits must not delay the transition aggregation.
- Redis lists are cheap; three is fine.

**Why Redis and not Postgres LISTEN/NOTIFY**
- Redis is already deployed (`vpt-discard-incidents` uses it).
- Survives the vpt-server being restarted.
- The writer on the host does not need direct DB write access to push to the queue.
- Postgres NOTIFY would tie the writer to a DB connection — the exact coupling we are breaking.

## Numbers
- **5 host × 1 Hz = 432k rows/day without throttling** → **~5 rows/sec fleet-wide** with the throttled `normal` channel plus the prioritised `change` and `alert` channels.
- Monitor pipeline overhead: **+0.1ms per frame** (one Redis LPUSH). Worst case (Redis down): matcher keeps running, the queue path logs at debug and skips the write.
- Worker is one process; on a 5-host fleet it handles the entire 1-Hz fleet with ~5% CPU.

## Open follow-ups
- **Profile-aware throttling**: today every profile gets the same 10s throttle. `drone` and `counting_cars` could safely run unthrottled; `tv_app` could run at 30s without losing insight. Per-profile overrides are a one-liner in the worker — flag for tuning.
- **Backfill of the `profile` column on existing rows**: the migration adds the column with NULL, which is correct (we cannot infer the profile retroactively). Future rows are tagged.
- **Worker metrics**: no `/server/match-runs-writer/health` route yet; the journalctl + `match_runs_queue.queue_lengths()` is what the operator has today. A small `wpt_heartbeat` table would let Grafana graph worker lag.
