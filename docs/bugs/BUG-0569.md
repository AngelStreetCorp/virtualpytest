# BUG-0569

## Symptom
BUG-0562 shipped `match_runs` + the post-verify cross-check + `v_node_transitions` / `v_uncertain_hits` / `v_recent_sequence` views, and BUG-0565 wired the monitor path through a queue + worker. The data is there but the operator has no way to *see* it: the existing `MatchRuns.tsx` was three raw tables under one tab strip. The Grafana dashboard had nine panels but no per-profile view, no auto-classify backlog, and the transitions panel was a flat table.

A dedicated dashboard needs to answer, at a glance:
- Is the matcher healthy right now? (live status strip)
- Where are the failures coming from — verify or live monitor? (verdict distribution over time)
- Is *this* device the problem or is the fleet the problem? (per-device matchers)
- What should I label next? (uncertain hits backlog)
- Verify failed — what was the device navigating? (sequence replay)
- Are all my profiles still healthy? (per-profile activity on Grafana)
- What will auto-classify pick up tonight? (auto-classify backlog on Grafana)
- What's actually happening in the navigation graph? (top transitions as a grouped bar on Grafana)

The first five are operator-page drills (one team, one UI, one device); the last three are cross-fleet Grafana views. Two surfaces, one data layer.

## Fix

### Operator page (5 panels on `frontend/src/pages/MatchRuns.tsx`)

The three-tab layout became a single-page layout with the same `StatTiles` strip across the top, the same six tile shapes (`Total`, `Match rate`, `Uncertain %`, `Unknown %`, `Active devices`, `Avg confidence`), and four cards stacked under it. The hook (`useMatchRuns`) calls all six endpoints in parallel and auto-refreshes every 10 s by default.

1. **Live status strip** — six tiles with a `1h / 6h / 24h / 7d` toggle. The `Match rate` tile turns red below 50 % and orange between 50 % and 80 % — the same thresholds the rest of the page uses (`rateColor` in `PageChrome`). Below the strip, a row of profile chips shows every matcher profile that wrote in the window.

2. **Verdict distribution** — a stacked bar over hourly buckets, series = {matched, low_confidence, no_signal, unknown, overlay}. Built from the existing recharts `StackedBar` in `frontend/src/components/analytics/Charts.tsx`; same xKey/series API the analytics pages already use.

3. **Per-device matchers** — one row per (host, device) in the window. Each row shows its match-rate (color-coded) AND a row of small square heatmap cells (one per run, ordered, match-rate-coloured), so a glance answers "all matched" vs "all missed". Click a row → the device field auto-fills the sequence replay picker.

4. **Uncertain hits backlog** — the top 20 from `v_uncertain_hits`, sorted by margin asc. Same columns as the existing Uncertain tab — Winner / Runner-up / margin / Frame link — now promoted from a tab to a panel so the operator doesn't need to click a tab to see it.

5. **Sequence replay** — Device + UI pickers, driven by the heatmap rows (device) and the recent window (UI). Selecting both runs a `POST /server/match-runs/sequence` and renders the last 20 events for that chain, columns = Step / Started / Source / Verdict / Top-1 / Top-2 / Top-3 / Margin. That's the panel the operator stares at when a verify fails: "where did the device go between the prompt and the target?"

The hook (`useMatchRuns`) now exposes `summary`, `perDevice`, `distribution`, `lastFetchedAt`, and a `window` filter (`'1h' | '6h' | '24h' | '7d'`). Default `refreshMs` is 10 000; set `0` to disable. `useMatchRunSequence` is a sibling hook that only fetches when the pickers have a value, so an empty state doesn't cost a query.

### Grafana (`infra/monitoring/grafana/dashboards/fingerprints.json`)

The existing 9 panels stay; 3 new panels are added at the bottom in id 10–12. The first two reuse the `userinterface_name` and `device_name` template variables that already drive the rest of the dashboard.

6. **Per-profile activity** — `bar chart`, one bar per `profile`, stacked by `verdict`. ANSWERS: "are all my matcher profiles still healthy?". SQL: `SELECT profile, verdict, COUNT(*) FROM public.match_runs WHERE started_at >= ... AND profile IS NOT NULL GROUP BY 1, 2`.

7. **Auto-classify backlog** — `table`, top 50 unknowns with `seen_count >= 5` and `classification_attempts < 3`, columns: `scope`, `dhash`, `first_seen_at`, `seen_count`, `last_seen_at`, `proposed_name`. The nightly `auto-classify.timer` is targeting these rows; the panel exists so the operator can see what is queued.

8. **Top transitions heatmap** — the existing panel 7 was a `table` ordered by `occurrences`; the new panel 12 is the same source data but rendered as a grouped horizontal bar (`from_node_id` on the y axis, `occurrences` on x) so a glance answers "which from-node has the most destinations?". Native Grafana panels don't ship a from×to heatmap without a plugin, so the bar is the right shape.

### Server endpoints (`backend_server/src/routes/server_match_runs_routes.py`)

Four new read endpoints, all guarded by `handle_route_exceptions`. They take `{team_id, window?, since?, userinterface_name?, device_name?, device_id?, session_id?, limit?}` and return the rows the front-end needs.

- `POST /server/match-runs/summary` → `{row: MatchRunSummary, window_started_at}`
- `POST /server/match-runs/per-device` → `{rows: MatchRunDeviceRow[], count}` (max 30 on the page)
- `POST /server/match-runs/distribution` → `{rows: {bucket, verdict, count}[]}` (one row per hour per verdict)
- `POST /server/match-runs/sequence` → `{rows: MatchRun[]}` (last `limit`, default 20, for one device+UI, optional session filter)

`_resolve_since(payload)` is the helper that decides the window: takes an explicit ISO `since` (capped at 7 d back), otherwise the named `window` (`1h`/`6h`/`24h`/`7d`, default `24h`).

### DB layer (`shared/src/lib/database/match_runs_db.py`)

Four new aggregations on top of the existing `list_recent`, `transitions`, `uncertain_hits`. The per-host/per-device bucketing and the verdict tally happen in Python (one SELECT each) — same supabase-client pattern the rest of the module uses.

- `summary(team_id, since_iso, ui, dev)` → KPI counts (total / matched / uncertain / unknown_or_low_conf / distinct_devices / distinct_profiles / distinct_hosts)
- `per_device(team_id, since_iso, ui)` → bucketed by `(host_name, device_name)`
- `verdict_distribution(team_id, since_iso, ui)` → bucketed by hour, in Python (avoids needing aggregate routes)
- `sequence(team_id, device_id, userinterface_name, session_id, limit)` → last N rows with `candidates_top_3` and `runner_up_margin` intact

### Smoke test (`scripts/smoke_match_runs_dashboard.sh`)

The existing smoke (`smoke_match_runs.sh`) covers the table + views + endpoints. The new one adds four assertions: `/summary` returns `{row.window_started_at}`; `/per-device` returns rows; `/distribution` returns rows; `/sequence` returns a row for the smoketest chain. Runs against the vpt-server with `X-API-Key` (same auth-aware probe pattern). `<60s`.

### Unit tests (`tests/unit/database/test_match_runs_dashboard.py`)

12 cases for the four new functions. Each function gets: (a) a happy-path sample with assertions on counts and ordering; (b) a row-shape check that confirms the columns the front-end consumes (`last_match_at`, `bucket`, `window_started_at`, `session_id`). Tests use a small in-memory list of dicts with a stubbed supabase client — same harness as the existing `test_match_runs_db.py`.

## Result

Operator opens `/match-runs` after a verify fails → status strip says "24h, 312 runs, 94 % match" → verdict distribution shows the spike is in `verify` not `monitor` → per-device heatmap singles out one device → sequence replay shows the 20 events for that device in that UI, runner-up margin highlighted on the failing row. Grafana `/d/fingerprints` shows the same fleet-wide, plus the per-profile view, the auto-classify backlog, and the top transitions as bars. The matcher goes from "we have the data somewhere" to "we have a dashboard we look at".
